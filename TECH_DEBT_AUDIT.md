## Executive summary

- **Highest-severity finding**: the Compare-view donut chart (`buildDonut`, `server.js:2363-2389`) accumulates per-category arc length/offset without clamping to the circle's circumference. Whenever total ideal or actual hours exceed 168 — which `PRODUCT.md` and the app's own insight copy (`server.js:2421`, "your ideal week is over the 168 target") call out as the **expected common case**, not an edge case — segments silently overlap and later categories paint over earlier ones on the same arc.
- Two independent, ~150-line spotlight/tooltip walkthrough engines (`startTour` at `server.js:3193-3341` and `startTutorial` at `server.js:3436-3608`) duplicate positioning, keyboard-nav, and lifecycle logic that could be one parameterized engine.
- The History tab shows two disagreeing "total hours" numbers for the same snapshot because the snapshot-list total (`server.js:2630-2633`) and the diff-table total (via `snapRowHours`, `server.js:2678-2684`) use different fallback chains — one skips the `ideal` fallback the other has.
- Two per-row data fields seeded with real content for every one of the 20 default categories — `group` (emoji) and `hint` (tooltip text), documented in `data/categories.js:9-10` as "shown on the row" — are never read or rendered anywhere in `server.js`. Dead data for an apparently-intended feature.
- The share-link import path (`server.js:2946-2977`) is a genuine trust boundary (anyone can craft and send a `#share=` URL) with no schema/type validation beyond "is `rows` an array," and lets an attacker-supplied `id` silently override the generated unique row id via `Object.assign` argument order (`server.js:2969`).
- None of the three localStorage schema-migration tiers in `loadState()` (`server.js:1845-1925`) have test coverage, despite running on every returning user with pre-v3 data.
- `buildPage()`/`getCSS()`/`getJS()` rebuild the entire ~150KB, request-invariant HTML/CSS/JS payload from scratch on every GET (`server.js:25-28`) — cheap to fix, currently harmless only because traffic is trivial.
- `saveState()`'s catch block (`server.js:1927-1931`) silently swallows quota/serialization errors with no user-facing signal, unlike `takeSnapshot()` (`server.js:1949-1952`) which does toast on `QuotaExceededError` — the good pattern exists but isn't applied to the far more common save path.
- Two near-duplicate "collect answered reflection prompts, format as markdown" implementations (`reflectSection`, `server.js:2875-2884`, vs `sect`/`answered`, `server.js:2902-2909`) diverge in output formatting and ship an unused `prefix` parameter.
- No security-relevant dependency issues (`npm audit`: 0 vulnerabilities across 71 packages); Express is one major behind (4→5), and Express 5's stricter path-to-regexp would reject the bare `"*"` route wildcard used at `server.js:25` — a latent upgrade trap, not a current bug.

## Architectural mental model

`server.js` is a single Express process with exactly three real routes: `/health`, `/favicon.svg` (+ `.ico` redirect), and a catch-all `GET *` that always returns the same server-rendered HTML shell (`buildPage()`). There is no server-side data model, no database, no auth, no per-request branching — the entire product is a client-side single-page app (state, rendering, export, all in `getJS()`) bootstrapped with seed data from `data/categories.js` and persisted entirely in the browser's `localStorage` (schema versions v1 → v2 → v3, migrated in-browser on load). `buildPage()` is deterministic given the module's static requires; nothing in it varies per-request, which is itself one of the findings below.

The client JS is a single IIFE (`server.js:1795-3667`, ~1,870 lines) organized into clearly-commented sections (State, Snapshot helpers, Theme, Worksheet, Compare, Reflect, History, Export, Profile picker, Tour, Tutorial, Global keyboard shortcuts, Init) — this is a reasonable internal structure for a no-build-step single file, and the section comments do genuine work as a poor man's module boundary. The house convention (single file, inline HTML/CSS/JS, no bundler, matching sibling projects `conference-tracker` and `site-runtime-baseline`) is documented in `CLAUDE.md` and is a deliberate, working choice for this project's size and audience — see "looks bad but is fine" below; it is not re-litigated as a finding.

Within that constraint, `getCSS()` (`server.js:202-1792`, ~1,590 lines) and `getJS()` (`server.js:1793-3669`, ~1,876 lines) are both god-functions by any line-count threshold, but that's an artifact of the house pattern, not itself flagged as debt — the actual debt is the duplication and inconsistency *within* them (tour/tutorial engines, reflection-formatting helpers, hours-fallback logic), which is what the findings below target.

## Top 5 — if you fix nothing else, fix these

1. **F001 — Fix donut chart overflow past 168h** (`server.js:2363-2389`). This is the single most product-relevant bug: the app's own copy tells users to expect an over-168h ideal week, then the primary visualization for that exact case silently overlaps segments.
   ```js
   // in buildDonut(), before the cats.forEach loop:
   const scale = sum > TARGET ? TARGET / sum : 1;
   // then inside the loop:
   const frac = (v * scale) / TARGET;   // was: v / TARGET
   ```
   (Keep `unalloc`/empty-state logic unchanged — it already only fires when `sum <= TARGET`.)

2. **F002 + F005 — Unify the three "effective hours" implementations** into one call to `snapRowHours()`. Fixes the disagreeing History totals and removes two of the three divergent fallback chains in one change.
   ```js
   // server.js:2630-2633, replace:
   const total = s.rows.reduce(function(sum, r) {
     const h = r.actual !== undefined ? r.actual : (r.hours !== undefined ? r.hours : 0);
     return sum + (parseFloat(h) || 0);
   }, 0);
   // with:
   const total = s.rows.reduce((sum, r) => sum + snapRowHours(r), 0);
   ```

3. **F008 — Validate/sanitize share-link imports.** Strip attacker-controlled `id` before merge, type-check numeric fields, cap array length.
   ```js
   // server.js:2969, replace:
   rows: payload.rows.map(r => Object.assign({ id: "import-" + Math.random().toString(36).slice(2, 7), group: "", hint: "" }, r)),
   // with (drop r.id explicitly, keep generated id authoritative):
   rows: payload.rows.slice(0, 200).map(r => {
     const { id, ...rest } = r || {};
     return Object.assign({ group: "", hint: "" }, rest, { id: "import-" + Math.random().toString(36).slice(2, 7) });
   }),
   ```

4. **F003 — Extract a shared spotlight-walkthrough engine** for `startTour`/`startTutorial`. Largest-effort item on this list (L), but also the largest line-count reduction available (~150 duplicated lines) — worth scheduling as a dedicated pass rather than a quick win.

5. **F012 — Surface `saveState()` failures to the user** the same way `takeSnapshot()` already does, so a full-quota browser doesn't silently discard edits.
   ```js
   function saveState() {
     try {
       currentProfile().rows = rows;
       localStorage.setItem(STORAGE_KEY_V3, JSON.stringify(state));
     } catch(e) {
       if (e.name === "QuotaExceededError") showToast("Storage full — your last change wasn't saved.");
     }
   }
   ```

- **The whole "3,671-line single file, inline CSS/JS-as-strings, no bundler" shape.** This is the headline "looks bad" call, and it's explicitly the house convention (`CLAUDE.md`, matching `conference-tracker` and `site-runtime-baseline`), appropriate for a solo personal tool with no build pipeline and no team to coordinate module boundaries across. Not re-flagged as debt; the internal organization (named sections, consistent `escHtml`/`escAttr` usage) is doing real work to keep it navigable at this size.
- **`getCSS()`/`getJS()` as 1,500+/1,800+-line "god functions."** Same reasoning as above — they're two string-returning functions, not one entangled god *object* with mixed responsibilities. Splitting them would mean splitting the file, which is the thing the house convention explicitly opts out of.
- **The cascading `try { v3 } catch → try { v2 } catch → try { v1 } catch → fresh` migration ladder in `loadState()` (`server.js:1845-1925`).** Looks like duplication at first glance (three near-identical defensive-shape-check blocks), but each tier is genuinely gated on a different localStorage key and has to independently validate a different legacy shape before falling through — collapsing them into one parameterized loop would arguably be *harder* to follow than three linear, read-top-to-bottom tiers for a migration chain this short (3 versions). Only flagged for lack of test coverage (F009), not for the duplication itself.
- **Escaping discipline (`escHtml`/`escAttr`) across every `innerHTML` call site that touches user-editable data** (categories, sub-categories, notes, profile names, reflection answers, snapshot labels) — verified by reading every `innerHTML =` assignment in the file. This is the one place a "looks like it might be an XSS risk" instinct (user-controlled strings + string-built HTML + no framework auto-escaping) turns out to be unfounded: the pattern is applied correctly and consistently, including on the one genuine external-input path (share-link import).
- **`num()`'s `[0, 168]` clamp on every read of `ideal`/`actual`.** At first glance, having totals summed from unclamped stored values looks like a missing-validation gap — but every consumer (`sumIdeal`, `sumActual`, `byIdeal`/`byActual` in Compare, CSV/MD export) reads through `num()` or an equivalent inline clamp, so a corrupted/out-of-range stored value can't produce a nonsensical total. The one place this reasoning doesn't fully hold is F001 (the *sum* of clamped per-row values can still exceed the 168 target across the whole week, which is correct and intentional — the bug is the donut not handling that sum gracefully, not the per-row clamp).
- **`prompt()`/`confirm()` for profile rename/create/delete** (`server.js:3045,3059,3085`) read as dated UX at first glance, but for a keyboard-first personal tool with no design requirement to avoid native dialogs (`PRODUCT.md` explicitly deprioritizes "settings screens"), a blocking native prompt for an infrequent, low-stakes action is a reasonable trade against building a custom modal for three rarely-used actions.
